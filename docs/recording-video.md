# 通过协议下载会议视频

需要结合会议共享画面整理记录，而 `tmeet record address` 只返回回放页面时，可使用 `online/recordings.py`。它用官方 `wecom-cli` 定位会议的录制分享标识，再复用本机企业微信已有的录制会话，调用录制网页的下载协议。没有浏览器点击、缓存地址扫描、登录操作或分享设置修改。

当前支持 macOS 企业微信，2026-11-07 在 5.0.12 上实际下载了一份 126,789,736 字节的完整云录制。网页协议不是公开 REST API 的稳定契约，不能据此承诺其他客户端版本、操作系统或账号都可用。

## 调用

先用官方 CLI 按会议日期定位同一场会议：`wecom-cli meeting list` 得到 `mt...` 会议 ID；`tmeet record list` 或 `record search` 得到云录制的 `record_file_id`。两种 ID 不互换，不把同场的“文字转写”文件当成视频。

```bash
uv run online/recordings.py \
  --meeting-id '<企微 mt... 会议 ID>' \
  --record-file-id '<云录制 record_file_id>' \
  --output '/本机私有目录/会议.mp4'
```

依赖由脚本的 PEP 723 元数据声明，`uv` 复用其缓存，不修改企业微信或全局 Python。`wecom-cli` 不在 PATH 时传 `--wecom-cli /绝对路径/wecom-cli`。多账号时传 `--profile wew_...`，明确选择企业微信 CEF 账号目录；不自动猜账号。已有目标文件或 `.part` 文件不会被覆盖。

需要已存在且有效的企业微信录制网页登录态，并保持客户端运行以取得当前客户端信息。没有会话、会话过期、协议报错或下载权限不足时直接停止；不会自动扫码、取聊天数据库密钥、重签客户端或修改系统安全设置。会话只能按客户端正常流程恢复，不能把一次成功当成无需维护授权。

## 协议归属

1. `wecom-cli meeting get` 返回本场 `record_url`，只在进程内解析分享标识。
2. 仅读取企业微信 CEF 中 `meeting.tencent.com` 的 Cookie，由 `browser-cookie3` 解码当前版本使用的 Chromium mock-keychain 格式；不读取其他站点的登录态，不导出明文凭据。
3. 调用录制网页的 `get-multi-record-file`，按目标文件选择视频资源，必须得到 `downloadable=true`。
4. 调用 `sign-multi-record-file` 取得当前资源的临时地址，立即通过 HTTPS 下载。完整的原始回放页作为 Referer，保留 Range 请求。
5. 收到的字节数必须与文件接口的 size 一致，再将 `.part` 改为目标文件。输出只有会议／文件标识、文件大小和本机路径，异常不打印带签名的请求地址。

客户端请求由网页公共参数和企业微信桥接参数合并，包含重复字段及有意义的空字段。本次实测把参数折叠成字典或删掉空字段，会把同一账号的 `downloadable=true` 变成 false。实现保留实际参数序列；不要为“简化”改变它，也不要忽略服务器的权限判定。

Cookie、分享标识和签名地址不能进日志、文档或 Git。完整视频放本机私有目录；会议记录只保存必要且经过查看的关键帧、时间定位和来源文件标识。

## 与转写对应

按同一录制文件的相对时间取帧，例如使用 FFmpeg 的 `-ss 00:25:20 -i 会议.mp4 -frames:v 1 画面.jpg`。先定位讨论依赖画面的地方，再按需要细取，避免把整场压成一张无法阅读的缩略图。

图片应说明是实际页面、示例或原型、已完成历史会话，还是现场运行过程。相对时间、对应转写段落和任务一起记录。裁去浏览器地址栏、参会者栏及无关桌面区域；遮盖资源地址等内容时在图注说明，不修改业务证据。仅展示已完成会话不能证明现场耗时，资产的“已发布”也不等于产品版本已发版。
